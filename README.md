# ML System Design Doc - [RU]

## Дизайн ML системы - [Tubi Feedback Analyzer MVP v1](https://code.tubitv.com/using-pre-trained-nlp-models-to-interpret-user-feedback-at-tubi-6dffecf46510)

## 1. Цели и предпосылки

### 1.1. Зачем идем в разработку продукта?

* **Бизнес-цель:** Масштабировать процесс анализа тысяч ежедневных сообщений обратной связи от пользователей (NPS-комментарии, тикеты в поддержку). Текущий ручной анализ не масштабируется.
* **Почему станет лучше, чем сейчас:** Автоматизация позволит обрабатывать 100% обратной связи, отслеживать тренды и выявлять области для продуктовых улучшений быстрее и дешевле, чем ручной труд.
* **Что будем считать успехом итерации:** Создание моделей классификации, которые позволят отслеживать тренды категорий обратной связи на дашборде для использования продуктовой командой и командой поддержки.

### 1.2. Бизнес-требования и ограничения

* **Бизнес-требования:**
1. Классификация NPS-комментариев на категории: `Content`, `App`, `Ads`, `Features & Bugs`.
2. Классификация тикетов поддержки на категории: `Request`, `Issue`, `Inquiry`, `Complaint`, `Question`.
3. Возможность отслеживать динамику (тренды) этих категорий во времени.

* **Бизнес-ограничения:**
  * Ограничения по времени ответа системы: неизвестно
  * Ограничения по инфраструктуре: неизвестно
  * Ограничения по данным (качество разметки): частично размеченные данные

* **Что мы ожидаем от конкретной итерации:** Создание работающих моделей классификации и дашборда для отслеживания трендов.

* **Описание бизнес-процесса пилота:**
  Текстовые данные поступают в систему, далее проходят через ML-модель, после агрегируются категории визуализируются на дашборде и в конце используются продуктовой и support-командами для принятия решений.

* **Что считаем успешным пилотом:**

  * Модель достигает приемлемого качества классификации (F1 ≥ 0.8 для ключевых классов)
  * Дашборд корректно отображает тренды

### 1.3. Что входит в скоуп проекта/итерации, что не входит

* **На закрытие каких БТ подписываемся:**
1. Разработка моделей классификации для NPS и тикетов поддержки
2. Построение пайплайна эмбеддингов
3. Построение базового дашборда

* **Что не будет закрыто:**
1. Автоматический роутинг тикетов
2. Сентимент-анализ
3. Другие техники извлечение ключевых слов

* **Результат с точки зрения качества кода:**  
  Неизвестно.

* **Технический долг:**  
  Неизвестно.

### 1.4. Предпосылки решения

* **Данные:** Исторические NPS-комментарии и тикеты поддержки, частично размеченные

* **Гранулярность:** одно сообщение

* **Горизонт:** near real-time анализ

* **Техника:** Transfer Learning + классический ML

* **Обоснования:**  
  LightGBM - быстрый и устойчивый для эмбеддингов

## 2. Методология `Data Scientist`

### 2.1. Постановка задачи

Задача **мультиклассовой классификации текста** для двух доменов:

* NPS feedback
* Support tickets

### 2.2. Блок-схема решения

**Pipeline:**

Текст -> Encoder (USE/BERT) -> Embeddings -> LightGBM -> Класс -> Агрегация -> Дашборд

### 2.3. Этапы решения задачи

#### Этап 1 - Подготовка данных

* **Данные:**

    | Название данных | Есть ли данные в компании | Требуемый ресурс | Проверено ли качество данных |
    | :--- | :--- | :--- | :--- |
    | NPS комментарии | Да | Не указан | + |
    | Тикеты поддержки | Да | Не указан | + |
    | Метки категорий | Да (созданы вручную) | DS, Product/Support | + |

* **MVP:**

  * USE embeddings

  * Шум в тексте

* Целевая переменная:  
  Категория текста
* Метрики:  
  * F1-score (основная)
  * Accuracy
  * ROC-AUC

* MVP:  
  USE + LightGBM

#### Этап 4 - Интерпретация моделей

* MVP:

  Проверка категорий вручную
