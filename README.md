# ML System Design Doc - [RU]

## Дизайн ML системы - [Tubi Feedback Analyzer MVP v1](https://code.tubitv.com/using-pre-trained-nlp-models-to-interpret-user-feedback-at-tubi-6dffecf46510)

### 1. Цели и предпосылки

#### 1.1. Зачем идем в разработку продукта?

* **Бизнес-цель (`Product Owner`):** Масштабировать процесс анализа тысяч ежедневных сообщений обратной связи от пользователей (NPS-комментарии, тикеты в поддержку). Текущий ручной анализ не масштабируется, требует больших временных затрат и не позволяет оперативно реагировать на возникающие тренды.
* **Почему станет лучше, чем сейчас, от использования ML (`Product Owner` & `Data Scientist`):** Автоматизация позволит:
    1. обрабатывать 100% входящей обратной связи;
    2. отслеживать динамику изменения категорий проблем во времени на дашборде;
    3. быстрее выявлять области для продуктовых улучшений и приоритизировать инициативы;
    4. сократить время и стоимость анализа, по сравнению с содержанием команды для ручной разметки;
    5. заложить основу для будущей автоматической маршрутизации тикетов.
* **Что будем считать успехом итерации с точки зрения бизнеса (`Product Owner`):** Успехом итерации будет создание и внедрение моделей классификации, которые позволят продуктовой команде и команде поддержки отслеживать тренды категорий обратной связи на централизованном дашборде и использовать эти данные для принятия обоснованных решений.

#### 1.2. Бизнес-требования и ограничения

* **Бизнес-требования:**
    1. Разработать модель для классификации NPS-комментариев по категориям: `Content`, `App`, `Ads`, `Features & Bugs`;
    2. Разработать модель для классификации тикетов службы поддержки по категориям: `Request`, `Issue`, `Inquiry`, `Complaint`, `Question`;
    3. Обеспечить возможность отслеживать динамику этих категорий во времени (например, ежедневно или еженедельно);
    4. Модели должны работать на обоих источниках данных.
* **Бизнес-ограничения (`Product Owner`):**
  * **Качество данных:** Исходные данные не размечены. Для обучения потребуется ручная разметка репрезентативной выборки, что является единоразовой, но трудоемкой задачей.
  * **Временные рамки:** Не указаны в статье, но подразумевается, что решение нужно было разработать в разумные сроки (вероятно, несколько недель/месяцев).
  * **Интерпретируемость:** Бизнес-пользователям (PO, support) необходимо понимать, почему комментарий отнесен к той или иной категории, чтобы доверять модели.
* **Что мы ожидаем от конкретной итерации (`Product Owner`):** Рабочие модели классификации с приемлемым качеством (precision/recall) и дашборд для визуализации трендов.
* **Описание бизнес-процесса пилота:** Текстовые данные (NPS/тикеты) поступают в систему -> проходят через ML-пайплайн (эмбеддинги -> классификация) -> предсказанные категории сохраняются в БД -> данные агрегируются и визуализируются на дашборде -> продуктовая и support-команды анализируют тренды для принятия решений.
* **Что считаем успешным пилотом? Критерии успеха и возможные пути развития проекта (`Product Owner`):**
  * **Критерии успеха пилота:**
        1. Модели достигают целевых метрик качества на тестовой выборке (см. раздел 3.2);
        2. Дашборд успешно развернут и отображает актуальные данные;
        3. Команды продукта и поддержки подтверждают, что тренды на дашборде соответствуют их экспертной оценке и полезны для работы.
  * **Пути развития:** Автоматическая маршрутизация тикетов, сентимент-анализ, A/B-тестирование продуктовых изменений на основе обратной связи.

#### 1.3. Что входит в скоуп проекта/итерации, что не входит

* **На закрытие каких БТ подписываемся в данной итерации (`Data Scientist`):**
    1. Проведение EDA и ручная разметка достаточного количества данных для обучения/валидации;
    2. Разработка и сравнение моделей классификации на основе USE и BERT;
    3. Выбор финальной модели (USE + LightGBM) и ее обучение;
    4. Построение пайплайна для преобразования текста в эмбеддинги и предсказания классов;
    5. Разработка базового дашборда для отслеживания трендов.
* **Что не будет закрыто (`Data Scientist`):**
    1. Автоматический роутинг (assign) тикетов в соответствующие команды на основе классификации;
    2. Анализ тональности (sentiment analysis) комментариев;
    3. Извлечение ключевых слов (keyword extraction) для детализации проблем внутри категорий;
    4. Мультиклассовая модель (в данной итерации используются отдельные бинарные классификаторы для каждой категории);
    5. Реалтайм инференс (достаточно пакетной обработки, например, раз в день).
* **Описание результата с точки зрения качества кода и воспроизводимости решения (`Data Scientist`):** Код будет организован в виде модулей (обработка данных, модели, визуализация) с использованием ноутбуков для экспериментов и Python-скриптов для продуктивного пайплайна. Будет подготовлен `requirements.txt` и инструкция по запуску (README) для воспроизводимости результатов.
* **Описание планируемого технического долга (`Data Scientist`):**
  * Использование LightGBM вместо более сложных нейросетевых классификаторов для скорости и простоты;
  * Отсутствие автоматического переобучения моделей на новых данных (пока что планируется ручной рефрешинг при необходимости);
  * Ручной этап преобразования текста в эмбеддинги (в будущем можно объединить в один энд-ту-энд пайплайн).

#### 1.4. Предпосылки решения

* **Данные:** Исторические NPS-комментарии и тикеты поддержки на английском языке, хранящиеся в компании. Для обучения используется вручную размеченная выборка.
* **Гранулярность:** Единица анализа — одно текстовое сообщение (комментарий или тикет).
* **Горизонт прогноза:** Текущее состояние. Модель классифицирует уже поступившее сообщение.
* **Частота пересчета:** Модель обучается один раз на исторических данных. Планируется периодическое дообучение для учета дрейфа данных. Инференс может выполняться ежедневно.
* **Техника:** Использование **Transfer Learning** (предобученные модели эмбеддингов USE/BERT) для извлечения признаков из текста и классического ML-алгоритма (**LightGBM**) для классификации.
* **Обоснование выбора:** USE лучше подходит для задачи custom text classification по сравнению с BERT, что подтвердилось экспериментально. LightGBM выбран за скорость обучения, низкое потребление ресурсов и хорошее качество на табличных данных (эмбеддингах).

### 2. Методология `Data Scientist`

#### 2.1. Постановка задачи

Задача **мультиклассовой классификации текста** для двух независимых доменов: NPS feedback и Support tickets.

#### 2.2. Блок-схема решения

**Pipeline:**

`Сырой текст` -> `Предобработка (минимальная)` -> **`Encoder (USE)`** -> `Вектор эмбеддингов` -> **`LightGBM Classifier`** -> `Предсказанный класс` -> `Агрегация в БД` -> **`Дашборд (тренды)`**

* **Бейзлайн:** В качестве бейзлайна можно рассматривать простые правила (классификация по наличию ключевых слов "ad", "bug", "movie") или использование TF-IDF + Logistic Regression. Однако в статье сравнение идет сразу между USE и BERT, где USE выступает в роли более сильного базового решения.
* **MVP:** Финальная схема с USE + LightGBM.

#### 2.3. Этапы решения задачи `Data Scientist`

##### Этап 1 - Подготовка и анализ данных (EDA)

* **Данные:**

| Название данных | Есть ли данные в компании | Требуемый ресурс | Проверено ли качество данных |
| :--- | :--- | :--- | :--- |
| NPS комментарии | Да (внутреннее хранилище) | DE/DS | + (проверена читаемость, язык) |
| Тикеты поддержки | Да (внутреннее хранилище) | DE/DS | + (проверена читаемость, язык) |
| Метки категорий | Нет (создаются вручную) | DS, Product/Support | +/- (будет проверено согласованностью) |

* **Результат этапа:** Выполнен EDA, определена структура данных, выявлены основные паттерны. Создана и согласована с бизнесом инструкция по разметке. Вручную размечена выборка достаточного объема для обучения и тестирования по каждому домену (NPS, Support). Данные разделены на train/test.
  * ![Пример распределения категорий для NPS](https://miro.medium.com/v2/resize:fit:1172/format:webp/0*5FSHlNa1dVbccL88)
  * ![Пример распределения категорий для Support](https://miro.medium.com/v2/resize:fit:1112/format:webp/0*8ZfgyZxjoNoqTkap)

##### Этап 2 - Подготовка признаков (Feature Engineering)

* **Бейзлайн:** TF-IDF вектора.
* **MVP:**
  * Использование предобученной модели **Universal Sentence Encoder (USE)** для преобразования каждого текстового комментария в 512-мерный вектор эмбеддинга.
  * Минимальная предобработка текста (очистка от лишних пробелов, приведение к нижнему регистру) не требуется, т.к. USE обучен на сыром тексте, но может быть выполнена для единообразия.
* **Обоснование:** USE позволяет эффективно перенести знания, полученные на огромных корпусах текстов, и представить семантику предложения в виде плотного вектора, пригодного для ML-алгоритмов.
* **Риски:** Эмбеддинги могут быть нечувствительны к некоторому специфичному сленгу или терминам, характерным для платформы Tubi, что может потребовать дообучения (fine-tuning) в будущем.

##### Этап 3 - Обучение моделей классификации

* **Целевая переменная:** Бинарная метка (0 или 1) для каждой категории в рамках подхода "один-против-всех".
* **Метрики качества:**
  * **Основная:** F1-score (сбалансированная метрика, важна для потенциально несбалансированных классов).
  * **Дополнительные:** Accuracy, ROC-AUC.
* **MVP:**
  * Модель: **LightGBM**.
  * Кросс-валидация для подбора гиперпараметров.
  * Обучение отдельных классификаторов для каждой категории в двух доменах.
* **Результат этапа:** Обученные модели для каждой категории (8 моделей: 4 для NPS, 5 для Support), сохраненные в формате, пригодном для инференса. Получены метрики качества на тестовой выборке.
* **Бизнес-проверка:** Проверка предсказаний модели на небольшой выборке экспертами (Product/Support) для подтверждения, что модель "думает" как человек.

##### Этап 4 - Интерпретация моделей

* **MVP:** Анализ важности признаков (feature importance) из LightGBM. Поскольку признаки — это эмбеддинги, интерпретация будет сложной. Альтернативный подход: анализ ошибок модели и просмотр примеров, где модель ошибается, для выявления паттернов. Более продвинутая интерпретация (например, LIME или SHAP) запланирована как будущее улучшение.
* **Результат этапа:** Понимание основных причин ошибок модели, подтверждение, что она не использует неочевидные и невалидные корреляции.

##### Этап 5 - Инференс и сохранение результатов

* **MVP:** Разработка батч-пайплайна, который периодически:
    1. Забирает новые комментарии из источников;
    2. Прогоняет их через USE для получения эмбеддингов;
    3. Загружает обученные модели LightGBM и получает предсказания;
    4. Сохраняет предсказания (текст, категория, вероятность, дата) в аналитическую БД.

##### Этап 6 - Агрегация и визуализация

* **MVP:**
    1. Создание SQL-запросов для агрегации данных по дням/неделям: количество комментариев по каждой категории, доля категории в общем потоке.
    2. Разработка дашборда в Tableau/Power BI/DataLens, который отображает тренды категорий во времени.

##### Этап 7 - Сравнение и финальный отчет

* **MVP:** Сравнение финальной модели (USE + LightGBM) с альтернативой (BERT + LightGBM) по метрикам из статьи.
* **Результат этапа:** Презентация для стейкхолдеров с демонстрацией работы дашборда, финальными метриками моделей и планом по развитию.

#### Риски этапов и их mitigation

| Риск | Митигация |
| :--- | :--- |
| **Низкое качество/несогласованность ручной разметки** | Разработка четкого гайда по разметке. Привлечение нескольких экспертов для разметки одной выборки и расчет согласованности. |
| **Дисбаланс классов (категория `Inquiry` встречается очень редко)** | Использование метрик, устойчивых к дисбалансу (F1, ROC-AUC). Применение техник балансировки (например, взвешивание классов в LightGBM). |
| **Дрейф данных (Data Drift)** | Мониторинг распределения предсказаний модели во времени. Периодический пересчет метрик на свежей размеченной выборке. Планирование регулярного дообучения модели. |
| **Высокая вычислительная стоимость USE на большом потоке данных** | Оптимизация батч-обработки, использование GPU для инференса эмбеддингов. |

### 3. Подготовка пилота

#### 3.1. Способ оценки пилота

* **Офлайн-оценка:** Финальные метрики (F1, ROC-AUC) на отложенной тестовой выборке, размеченной экспертами.
* **Онлайн-оценка (экспертная):** В течение пилотного периода команда продукта и поддержки ежедневно анализирует дашборд и выборочно проверяет предсказания модели на свежих данных, чтобы подтвердить их релевантность.

#### 3.2. Что считаем успешным пилотом

* **Продуктовые метрики (`Product Owner`):**
    1. Достижение целевых значений F1-score для ключевых классов:
        * Для NPS: `ads`, `content`, `features_bugs` >= 0.85; `app` >= 0.75.
        * Для Support: `issue`, `request`, `question` >= 0.8; `inquiry`, `complaint` >= 0.6 (для редких классов допустимы более низкие значения, но с высоким precision).
    2. Продуктовая команда подтверждает, что тренды на дашборде помогают в принятии решений.

#### 3.3. Подготовка пилота

* **Вычислительные ресурсы:** Для пилота будет достаточно инстанса с CPU для запуска батч-пайплайна раз в день. Основные затраты — на этапе обучения. USE-энкодер может работать на CPU с приемлемой скоростью для тысяч комментариев в день.

### 4. Внедрение `для production систем, если требуется`

#### 4.1. Архитектура решения

1. **Источник данных:** БД с NPS-комментариями и тикетами поддержки.
2. **Оркестратор:** Apache Airflow для запуска ежедневного DAG-а.
3. **Вычислительный слой:** Python-скрипты (Docker-контейнеры), которые:
    * Выгружают новые данные.
    * Загружают модель USE из TensorFlow Hub.
    * Трансформируют текст в эмбеддинги.
    * Загружают `.pkl` файлы обученных LightGBM моделей и делают предсказания.
4. **Хранилище результатов:** Отдельная таблица в аналитической БД.
5. **Визуализация:** Инструмент BI, подключенный к аналитической БД.

#### 4.2. Описание инфраструктуры и масштабируемости

* **Выбор:** Облачные решения или on-premise кластер. Airflow для оркестрации, Docker для упаковки кода.
* **Масштабируемость:** При росте объема данных в 10-100 раз, батч-пайплайн можно масштабировать горизонтально, увеличивая ресурсы, выделенные на контейнеры с инференсом. Узкое место — USE на CPU, можно перейти на GPU-инстансы или использовать более легкую версию энкодера.

#### 4.3. Требования к работе системы

* **SLA:** Данные на дашборде должны обновляться ежедневно.
* **Пропускная способность и задержка:** Система должна обрабатывать до ~50,000 сообщений в день в рамках одного батча за 1-2 часа.

#### 4.4. Безопасность системы

* Доступ к дашборду и БД с результатами должен быть ограничен сотрудниками компании согласно их ролям.

#### 4.5. Безопасность данных

* Необходимо убедиться, что в текстах комментариев нет персональных данных или они удаляются до обработки.

#### 4.6. Издержки

* Хранение данных.
* Вычислительные ресурсы для ежедневного батча (~1-2 часа CPU).
* Стоимость инструмента BI.

#### 4.5. Integration points

* API не предполагается. Интеграция осуществляется через БД: пайплайн читает из одной таблицы и пишет в другую.

#### 4.6. Риски

* **Доступность модели из TensorFlow Hub:** В редких случаях Hub может быть недоступен. Необходим кэш модели на локальном или S3-хранилище.
* **Изменение формата данных:** Если изменится структура таблиц с исходными комментариями, пайплайн сломается. Требуется версионирование схем данных и алертинг при ошибках.

### 5. Гиперпараметры ML-решения

#### 5.1. Гиперпараметры энкодера (Universal Sentence Encoder)

* **Модель:** `Universal Sentence Encoder (Transformer)` - выбрана версия на основе Transformer-архитектуры (более точная, чем DAN).
* **Размерность эмбеддингов:** 512.
* **Параметры токенизации:** Используется встроенный токенизатор модели, внешняя предобработка не применяется (сохраняются оригинальный регистр и пунктуация, т.к. модель обучена на разнообразных текстах).

#### 5.2. Гиперпараметры классификатора (LightGBM)

Для каждой категории классификаторы обучаются с одинаковым набором гиперпараметров (после оптимизации).

* **Основные параметры:**
  * `boosting_type`: 'gbdt' (Gradient Boosting Decision Tree)
  * `objective`: 'binary' (бинарная классификация)
  * `metric`: 'auc' (метрика для оптимизации на валидации)
  * `num_leaves`: 31 (количество листьев в дереве)
  * `max_depth`: -1 (без ограничения)
  * `learning_rate`: 0.05 (скорость обучения)
  * `n_estimators`: 1000 (количество деревьев, с ранней остановкой)

* **Параметры регуляризации (для борьбы с переобучением):**
  * `min_child_samples`: 20 (минимальное количество данных в листе)
  * `subsample`: 0.8 (доля случайно выбираемых строк для каждого дерева)
  * `colsample_bytree`: 0.8 (доля случайно выбираемых признаков для каждого дерева)
  * `reg_alpha`: 0.1 (L1 регуляризация)
  * `reg_lambda`: 0.1 (L2 регуляризация)

* **Параметры ранней остановки:**
  * `early_stopping_rounds`: 50 (обучение останавливается, если метрика на валидации не улучшается 50 итераций)
  * `validation_split`: 0.2 (20% обучающих данных используется для валидации)

#### 5.3. Обработка дисбаланса классов

* **Взвешивание классов:** `class_weight`: 'balanced' (веса обратно пропорциональны частотам классов в обучающих данных). Это особенно важно для редких категорий, таких как `Inquiry` или `Complaint`.
* **Порог классификации:** Для каждой категории подбирается индивидуальный порог вероятности (threshold), оптимизирующий F1-score на валидационной выборке (стандартный порог 0.5 может быть неоптимален для несбалансированных классов).

#### 5.4. Параметры кросс-валидации

* **Метод:** Стратифицированная K-Fold кросс-валидация (сохраняет пропорции классов в каждом фолде).
* **Количество фолдов:** 5 (обеспечивает баланс между вычислительной сложностью и устойчивостью оценки).
* **Shuffle:** Да, перемешивание данных перед разбиением.

#### 5.5. Воспроизводимость

* **Random seed:** `42` (фиксируется для всех случайных процессов: разбиение данных, инициализация модели, subsample в LightGBM).

#### 5.6. Обоснование выбора гиперпараметров

* **`num_leaves = 31` и `max_depth = -1`:** Стандартное значение, хорошо работающее для большинства задач. LightGBM растет в глубину (leaf-wise), поэтому `num_leaves` важнее, чем `max_depth`. Значение 31 ограничивает сложность деревьев, предотвращая переобучение на эмбеддингах размерностью 512.
* **`learning_rate = 0.05` и `n_estimators = 1000`:** Умеренная скорость обучения в сочетании с большим количеством деревьев позволяет модели постепенно обучаться сложным паттернам. Ранняя остановка гарантирует, что мы не переобучимся, даже если укажем большое `n_estimators`.
* **`subsample` и `colsample_bytree = 0.8`:** Стандартные значения для стохастического градиентного бустинга, которые добавляют случайность в процесс обучения и улучшают обобщающую способность.
* **`reg_alpha` и `reg_lambda = 0.1`:** Легкая L1 и L2 регуляризация помогает отсеивать неважные признаки и сглаживать веса, что особенно полезно при работе с высокоразмерными эмбеддингами.
